## 3. Integration challenges and git history

### Identifier reconciliation

**CONFIRMED**. Internal UIDs canonicalize uppercase ticker keys, while the universe loader translates US share-class dots (for example `BRK.B` to Yahoo's `BRK-B`) and preserves exchange suffix dots. SEC access maps uppercase tickers to zero-padded ten-digit CIKs before requesting company facts and submissions; the IBKR Flex importer parses stock symbols and option/OCC contract attributes into normalized position IDs, rejects duplicate IDs, and preserves existing app-only metadata by position ID or underlying ticker. ### Conflicts, late arrivals, restatements, duplicates

**CONFIRMED**. The source registry records authority ranks and fallback IDs; for SEC instant balance-sheet facts with the same period end, the EDGAR parser keeps the latest `filed` entry, while DCF uses EDGAR for deeper quarterly history with a Yahoo fallback. The temporal repository treats an unchanged source payload/metadata as an idempotent no-op, stores business `valid_from` separately from ingestion `tx_from`, closes an overlapping current transaction version on correction, and links replacement versions with `supersedes_version_id`; PostgreSQL exclusion constraints prevent overlapping current valid intervals for the same object/relation UID. [ontology/sources/source_registry.py](ontology/sources/source_registry.py), [portfolio/momentum/fundamental_momentum/edgar_fetcher.py](portfolio/momentum/fundamental_momentum/edgar_fetcher.py), [equities/valuation/dcf.py](equities/valuation/dcf.py), [ontology/temporal_repository.py](ontology/temporal_repository.py), [migrations/versions/20260503_0011_temporal_ontology.py](migrations/versions/20260503_0011_temporal_ontology.py). **INFERRED**. The version model supports late-arriving and restated data without erasing what was previously known, but this audit did not validate source-by-source restatement correctness in a live database. [docs/architecture/ontology.md](docs/architecture/ontology.md), [ontology/temporal_repository.py](ontology/temporal_repository.py).

### Rate limits, retries, drift, backfills

**CONFIRMED**. Shared wrappers retry `yfinance`, HTTP 429/5xx, and FRED failures with exponential backoff; SEC requests are serialized/throttled, and market-breadth downloads are chunked. ## 4. Data model and approval path

- **CONFIRMED — bitemporality.** The authoritative PostgreSQL `source_record_versions`, `ontology_object_versions`, `ontology_relation_versions`, and `computed_snapshot_versions` tables have `valid_from`/`valid_to` for business truth and `tx_from`/`tx_to` for when Talisman recorded that truth. `TemporalOntologyRepository._temporal_where` applies valid-time `as_of` and transaction-time `tx_as_of` filters; default transaction reads require `tx_to IS NULL`, while corrections close an old transaction interval and add a linked version. [migrations/versions/20260503_0011_temporal_ontology.py](migrations/versions/20260503_0011_temporal_ontology.py), [ontology/temporal_repository.py](ontology/temporal_repository.py), [docs/architecture/ontology.md](docs/architecture/ontology.md).
- **CONFIRMED — provenance.** A source record stores vendor, source name/version, dataset, record key/hash, payload hash, as-of and load timestamps, quality/status, and `provenance_event_id`. Object/relation versions can point to the exact `source_record_id` through a foreign key and also carry provenance event, actor, action-run, approval, and input-hash metadata; `ObjectVersionRef` records exact versions produced by governed decisions. [migrations/versions/20260503_0011_temporal_ontology.py](migrations/versions/20260503_0011_temporal_ontology.py), [ontology/command_service.py](ontology/command_service.py), [docs/architecture/ontology.md](docs/architecture/ontology.md).
- **CONFIRMED — proposed write to commit.** A human route can call `stage_api_action`, Stan proposal tools call `propose_action_from_tool`, and workflow artifacts call `persist_artifacts`; each goes to `OntologyCommandService.propose_action`, which validates the action, evaluates policy, hashes input/base state, and records a pending `Approval`. An authorized reviewer calls the approvals route, which reaches `resolve_approval`; that checks policy, note, actor/role/quorum requirements and base-state freshness, then `_apply_approval` creates an `ActionRun`, `_write_action_targets` writes temporal object versions, and execution/version-reference/audit records are linked. [api/action_execution.py](api/action_execution.py), [api/agent_tools.py](api/agent_tools.py), [api/workflow_artifacts.py](api/workflow_artifacts.py), [ontology/command_service.py](ontology/command_service.py), [api/routers/approvals.py](api/routers/approvals.py), [ontology/command_service.py](ontology/command_service.py), [ontology/command_service.py](ontology/command_service.py).
- **CONFIRMED — scope of gate.** Agent *proposal* tools have no execute access and use that same approval path; the IBKR import explicitly stages with `apply=False`. Some API actions can use a self-apply path after policy checks, and safe automatic artifacts/non-actionable recommendations can be persisted without a pending approval, so “every write requires separate human approval” would be inaccurate. [ontology/action_registry.py](ontology/action_registry.py), [api/agent_tools.py](api/agent_tools.py), [api/routers/portfolio_edit.py](api/routers/portfolio_edit.py), [api/action_execution.py](api/action_execution.py), [ontology/command_service.py](ontology/command_service.py), [docs/architecture/ontology.md](docs/architecture/ontology.md).
