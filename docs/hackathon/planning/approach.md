# Longaeva approach v2

October 1, 2026 · Phase 1 · Proposed for review. October 9, 2026 and full submitted scope are confirmed. Revision v2 incorporates the user's requirement for an independently runnable submission ZIP/repository.

## Executive plan

**Recommendation.** Build a standalone Visa application, borrowing selected Talisman components and patterns. It may be developed in a self-contained directory within this checkout, provisionally `longaeva/`, whose contents become the root of a submission ZIP or fresh repository. It must run without the rest of Talisman. Keep React/FastAPI and a separately testable operating model. First validate a few dated public sources. The intended user is an investor deciding which business assumptions to change and what to research next. The hypothesis is that spending composition and revenue timing improve forecasts beyond aggregate growth; improvement remains unproven. (Submitted proposal, pp. 1–3.)

**Demo flow.** Open a saved Visa state and cutoff → inspect a dated passage and reviewed observation → accept a justified parameter range → run four quarterly transitions → compare revenue/profit distributions under shared draws → trace the change → show earnings/multiple valuation and cost-aware hold/add/trim/exit choices → inspect baselines, benchmarks and a failure case. One comparison conserves total spending while changing mix; another shows the service-revenue delay. Qualitative evidence may remain context without changing a number. (Proposal, pp. 2, 5–6.)

**What exists.** Talisman already has a research/dossier interface, evidence and citation records, analyst-feedback commands, generic provenance, temporal storage, chart components, and background-job patterns. Its current simulator consumes supplied stock-price moves and calculates position P&L; it does not generate outcomes from business activity. Its enabled document extractor produces a short text preview, not reviewed Visa operating observations. The main new work is the quarterly economic model, evidence-to-parameter review, saved reproducible runs, and business-forecast evaluation. Exact code evidence appears below.

**Integration choice.** Standalone packaging replaces v1's in-app route recommendation. Reuse portable chart code and adapt evidence/action patterns into the package; do not import Talisman's application services. Give it its own frontend/API entry points, dependencies, configuration, source/run storage and tests. Retain the proposal's PostgreSQL/SQLAlchemy architecture through an independently initialized database, provisionally a bundled Docker Compose service, plus local artifact storage and a small worker. No Talisman database, ontology services, portfolio state, login, cloud account or deployment configuration is required. This adds bootstrap and extraction effort but avoids broad app coupling. Any future Talisman integration is optional and depends on the standalone package, never the reverse.

**Submission boundary.** The export contains only the standalone code, dependency locks, setup/model documentation, tests, evaluation artifacts and permitted demo inputs. It excludes parent-repository imports, outside symlinks, developer-specific paths, secrets, personal data and Talisman's Git history. Provide one documented local startup command and a saved example that supports scenario changes and replay without LLM credentials; fresh extraction and the LLM benchmark use separately documented provider configuration. During the first vertical slice, export into a temporary directory outside Talisman and verify startup, scenario execution and saved-run replay there. Repeat against the final ZIP/fresh checkout. This is a planned packaging check, not a claim that an export exists. Actual organizer submission format remains unconfirmed.

**Tentative MVP: the submitted one-company system.** Keep structured AI extraction and review, four-quarter operating distributions, paired scenarios, saved replayable forecasts, valuation, illustrative actions with costs, investment benchmarks, all forecast baselines and all three ablations in scope. Eight eligible next-quarter historical forecasts remain the target, with earlier calibration history, extraction review, uncertainty scoring, prospective separation, a model specification, an evaluation report and a failure case. First build one dated state → one reviewed external observation → paired operating runs as a vertical slice; it is an intermediate milestone, not a reduced submission.

**Scope and proposal differences.** Full submitted functionality remains in scope, including valuation/actions, portfolio scoring, the same-document LLM benchmark and all three ablations. Standalone packaging changes the integration approach, not those commitments or the proposal's main stack. Historical consensus was conditional on licensed availability; use comparable guidance under its own label and report consensus unavailable unless a suitable free historical source is verified. Longaeva integration is also conditional and unavailable. Stretch beyond the submitted Visa deliverable includes a second company, broader source discovery and optional Talisman integration. A reusable company-model boundary remains in scope.

**Data choice.** Start feasibility checks with Visa filings, Booking Holdings travel disclosures, and Census retail tables; I-94 is a reserve corroborator. Then select a small set across the proposal's airline, travel-platform, retailer and payment-processor disclosures, each tied to a distinct driver. The shortlist is a starting gate, not the final coverage limit. The April 17 catalog's “BEA PCE” spending link actually points to a price index. This reinforces the recap's “Data Analysis Tools and Project Scoping”: select for sector relevance, measurable KPIs, data use, and repeatability.
